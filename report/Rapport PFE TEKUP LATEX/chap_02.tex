\chapter{Requirements Analysis and Specification}

\section*{Introduction}
\addcontentsline{toc}{section}{Introduction}
This chapter says what the PMS system has to do. It names the actors, lists the functional and
non-functional requirements, and sets out the business rules. It then presents the dynamic
authorization model, which shapes the whole platform, and the global use case diagram that follows
from it. The chapter closes with the product backlog, and shows how its stories are spread over
the sprints of the following chapters.
\section{Requirements specification}
This section states what the platform must do and for whom. It identifies the actors first, then
the functions the platform owes them, then the qualities it must hold while delivering those
functions, and last the business rules that constrain both.

\subsection{Non-functional requirements}
\begin{itemize}
    \item \textbf{Performance}: response in under two seconds for routine operations (NFR-001).
    \item \textbf{Security}: mandatory JWT authentication, hashed passwords (NFR-002).
    \item \textbf{Authorization}: permission-based access control (dynamic RBAC, NFR-003).
    \item \textbf{Maintainability}: clean, modular, feature-oriented architecture (NFR-006).
    \item \textbf{Scalability}: support for growth and future integration (ERP, HR, accounting)
    without rewriting the core (NFR-005, BR-065).
    \item \textbf{Auditability}: history preservation and logical deletion (NFR-008).
    \item \textbf{Usability}: intuitive and responsive interface (NFR-007).
\end{itemize}

\section{Global use case diagram}
Figure~\ref{fig:uc} presents the global use case diagram of the platform. The four actors are
associated with the business use cases falling within their perimeter, in strict accordance with
the boundaries stated in Table~\ref{tab:acteurs}: the administrator holds no project use case, and
the developer holds no financial use case.

The diagram is deliberately drawn at the level of the functional domain rather than the individual
operation. ``Manage projects'' covers creation, configuration, the assignment of a project manager,
closure and archiving; ``Manage project execution'' covers the team, the workload plan and its
validation, and the iterations. Decomposing each of these into its elementary operations would
produce a diagram of some forty ellipses that no longer shows what the system does, only how it is
implemented. The detailed operations appear in the use case diagram of the sprint that delivers
them, in Chapters~4 to~7.

Any functionality requiring a prior identification points to the ``Authenticate'' use case through
an \textit{include} relation, which avoids repeating the same association on each actor. The
``Freeze the monthly review'' use case extends ``Monitor performance indicators'' through an
\textit{extend} relation: consulting the indicators is the nominal behaviour, and freezing them
into a snapshot happens only at the monthly review.

\section{Class diagram}
\label{sec:class-diagram}
Figure~\ref{fig:class-global} gives the overall map of the domain. The project is the aggregation
root: most business entities exist only within a project and are composed by it, while users,
roles, permissions and resources form an independent reference core.

\begin{figure}[H]
  \centering
  \includegraphics[width=\columnwidth]{img/class_global.png}
  \caption{Domain model --- principal classes and their associations}
  \label{fig:class-global}
\end{figure}

One reading of the diagram deserves to be made explicit, because it is easy to expect the
opposite. The four roles of the platform are not subclasses of \texttt{User}: they are rows of
the \texttt{Role} class. A user holds a role, and a role grants permissions, so the authorization
policy is data that an administrator edits rather than a hierarchy compiled into the application.
Modelling the roles as types would have contradicted that, and would have made every change of
policy a new version of the software.

The diagram stays at the level of the principal classes and their key attributes. Each sub-domain
is detailed by its own class diagram, presented in the sprint that builds it: projects and teams in Sprint~3, agile planning in
Sprint~5, financial management in Sprint~6, governance in Sprint~7, and the indicator engine in
Sprint~8.

The authorization policy is the part of that model the rest of the platform depends on, and it is
worth its own reading.

The central architectural requirement of the project is to \textbf{never couple a role directly to
a module}. Such a coupling (``ROLE $\rightarrow$ MODULE'') would require modifying and redeploying
the code every time the company decides that a given profile may access an additional function.

The model retained therefore inserts an intermediate level:

\begin{center}
\textbf{Role $\rightarrow$ Permission $\rightarrow$ Module}
\end{center}

A role holds a set of permissions; each permission authorises a precise operation on a module. The
role--permission matrix lives in the database, not in the source code: granting a new right becomes
a data change, applied without redeployment. This principle governs the whole platform and is
verified in Sprint~2 (Chapter~4). Figure~\ref{fig:rbac-model} contrasts the two models on one
concrete right: the one that lets a project manager edit a project.

\begin{figure}[H]
  \centering
  \includegraphics[width=\columnwidth]{img/rbac_chain.png}
  \caption{Binding a role to a module, and the permission level that replaces it}
  \label{fig:rbac-model}
\end{figure}

Figure~\ref{fig:class-rbac} states the same model as a class diagram. A user holds one role, a
role grants a set of permissions, and a permission belongs to a functional module. None of the
four classes owns another, so every relation is a plain association.

\begin{figure}[H]
  \centering
  \includegraphics[width=\columnwidth]{img/class_rbac.png}
  \caption{Class diagram of the dynamic authorization model}
  \label{fig:class-rbac}
\end{figure}

reproducing on the platform a computation the workbook already performed and comparing the two
figures.

\section*{Conclusion}
\addcontentsline{toc}{section}{Conclusion}
This chapter set out what the platform must do, for whom, and under which rules. Those
requirements became a product backlog, spread over the development sprints. The next chapter
presents the architecture the construction rests on: the design models, the data model and the
database schema.
