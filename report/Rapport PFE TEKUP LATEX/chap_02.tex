\chapter{Requirements Analysis and Specification}

\section*{Introduction}
\addcontentsline{toc}{section}{Introduction}
This chapter formalises the business analysis of the PMS system. It identifies the actors, lists
the functional and non-functional requirements, presents the business rules and the dynamic
authorization model that structures the whole platform, and derives from them the global use case
diagram. It closes with the product backlog and its distribution across the development
sprints presented in the following chapters.

\section{Non-Functional Requirements}
\begin{itemize}
    \item \textbf{Performance}: response in under two seconds for routine operations (NFR-001).
    \item \textbf{Security}: mandatory JWT authentication, hashed passwords (NFR-002).
    \item \textbf{Authorization}: permission-based access control (dynamic RBAC, NFR-003).
    \item \textbf{Maintainability}: clean, modular, feature-oriented architecture (NFR-006).
    \item \textbf{Scalability}: support for growth and future integration (ERP, HR, accounting)
    without rewriting the core (NFR-005, BR-065).
    \item \textbf{Auditability}: history preservation and logical deletion (NFR-008).
    \item \textbf{Usability}: intuitive and responsive interface (NFR-007).
\end{itemize}

\section{The Dynamic Authorization Model}
\label{sec:rbac}
The central architectural requirement of the project is to \textbf{never couple a role directly to
a module}. Such a coupling (``ROLE $\rightarrow$ MODULE'') would require modifying and redeploying
the code every time the company decides that a given profile may access an additional function.

The model retained therefore inserts an intermediate level:

\begin{center}
\textbf{Role $\rightarrow$ Permission $\rightarrow$ Module}
\end{center}

A role holds a set of permissions; each permission authorises a precise operation on a module. The
role--permission matrix lives in the database, not in the source code: granting a new right becomes
a data change, applied without redeployment. This principle governs the whole platform and is
verified in Sprint~2 (Chapter~4). Figure~\ref{fig:rbac-model} contrasts the two models on one
concrete right: the one that lets a project manager edit a project.

\section{Global Use Case Diagram}
Figure~\ref{fig:uc} presents the global use case diagram of the platform. The four actors are
associated with the business use cases falling within their perimeter, in strict accordance with
the boundaries stated in Table~\ref{tab:acteurs}: the administrator holds no project use case, and
the developer holds no financial use case.

The diagram is deliberately drawn at the level of the functional domain rather than the individual
operation. ``Manage projects'' covers creation, configuration, the assignment of a project manager,
closure and archiving; ``Manage project execution'' covers the team, the workload plan and its
validation, and the iterations. Decomposing each of these into its elementary operations would
produce a diagram of some forty ellipses that no longer shows what the system does, only how it is
implemented. The detailed operations appear in the use case diagram of the sprint that delivers
them, in Chapters~4 to~7.

Any functionality requiring a prior identification points to the ``Authenticate'' use case through
an \textit{include} relation, which avoids repeating the same association on each actor. The
``Freeze the monthly review'' use case extends ``Monitor performance indicators'' through an
\textit{extend} relation: consulting the indicators is the nominal behaviour, and freezing them
into a snapshot happens only at the monthly review.

weeks; the two shorter ones cover the smaller perimeters, namely agile planning and interface
consolidation. The report itself is not a phase of the schedule: it was written throughout the
internship, each chapter being drafted as the work it describes was carried out, and only reviewed
