\chapter{Release 4: Consolidation, Delivery and Deployment}

\section*{Introduction}
\addcontentsline{toc}{section}{Introduction}
The platform was functionally complete at the end of Release~3. This last release makes it ready
to deliver. It brings one coherent and accessible interface, an authorization policy checked by
tests, a security review, and a deployment anyone can reproduce. Two sprints do that work.
Sprint~9 unifies the interface and verifies the platform. Sprint~10 makes it deployable on any
host and checks every change automatically. Neither sprint adds a business feature. Together they
turn a working application into one that can be handed over.

\subsection{Design}
This sprint adds no use case. It acts on those already delivered, by unifying the screens through
which they are reached and by verifying that the authorization attached to each of them behaves as
specified. The relevant view is therefore not a new use case diagram but the global one of
Chapter~2, now entirely covered by the interface.

\runin{Where authorization is decided}
The interface consumes the permission list returned by the context endpoint and derives from it both
the navigation menu and the visibility of individual actions. A button the user is not entitled to
use is not merely disabled: it is absent.

This must be understood correctly, and the report states it explicitly: hiding a control is an
\textbf{ergonomic} measure, not a security measure. The authorization decision is taken by the
server on every request, as described in Sprint~2. The client-side rule exists so that the user is
never offered an action that would be refused; it is never the thing that refuses it.

\runin{Design decisions}
\textbf{A design system rather than eight sets of screens.} The modules were built successively,
each with its own screens. Rather than harmonising them by hand, a token-based visual language,
covering colours, typography, spacing and elevation, is declared once and consumed everywhere, with
a set of shared components reused rather than reimplemented. Harmonising by hand would have left the
next module free to diverge again.

\textbf{Testing concentrates on what a regression makes expensive.} Not everything is worth an
automated test. The suite covers the business rules and the authorization model: lifecycle
transitions, the billing ceiling, workload uniqueness and immutability, multi-currency conversion,
and the indicator formulas compared against the reference workbook.

\textbf{Access control is tested in both directions.} For each protected endpoint the suite asserts
that a caller holding the permission succeeds \emph{and} that a caller without it is refused.
Testing only the success path would leave the platform's central claim unverified: it is the refusal
that proves the policy is enforced.

\subsection{Implementation}
The consolidation acted on the frontend as a whole rather than on any single module, and is
followed here by the verification work and by what packaging alone does not settle.


\runin{Frontend structure and session handling}
The client is a single-page application organised by feature, mirroring the backend modules. The
access token obtained at sign-in is kept in memory and attached to every request by an HTTP
interceptor; the refresh token remains in its \texttt{HttpOnly} cookie, unreachable from JavaScript.
When a request returns \texttt{401}, the interceptor attempts a single refresh before returning the
user to the sign-in screen.

\runin{Interface consolidation}
Beyond the visual language, the consolidation addressed accessibility and consistency: sortable
table headers announcing their state, labelled icon-only controls, explicit empty states in place of
blank tables, and a responsive layout. The interface being the only part of the platform its users
ever see, this convergence matters as much to adoption as the correctness of the engine behind it.

\runin{Packaging, and what it does not solve}
At the close of this sprint the platform is packaged as an executable archive for the backend and a
static build for the frontend, with the schema brought up to date by the migration tool at startup
and all configuration supplied by environment variables. Startup is idempotent: deploying the same
artefact against an up-to-date database changes nothing, and against an older one applies exactly
the missing migrations.

This is sufficient to \emph{run} the application but not to \emph{deploy} it reproducibly: it still
assumes a host on which the right Java version, the right Node version and a correctly provisioned
PostgreSQL instance are already present. Sprint~10 removes that assumption.

\subsection{Design}
Like the previous one, this sprint adds no business use case. Its actor is not a user of the
platform but the person deploying it, and its scenarios are building the images, starting the stack
and verifying a change automatically. The deployment view of Chapter~3 is the relevant diagram.

\runin{Docker}
\textbf{Docker} packages an application together with everything it needs to run --- runtime,
libraries, configuration --- into an image that behaves the same way on any host. A running copy of
that image is a container: isolated from the machine, started and stopped in seconds, and identical
whether it runs on a laptop or on a server.

It was chosen for the gap this sprint exists to close. Until now the platform assumed a host on
which the right Java version, the right Node version and a correctly provisioned PostgreSQL were
already present, which is an assumption that holds on the development machine and nowhere else.
Describing those dependencies as images removes the assumption: the stack starts from one command,
and the environment stops being something a person has to reproduce by hand. The alternative
considered was a documented installation procedure, which was rejected because a procedure is only
as reliable as the person following it.

\begin{figure}[H]
  \centering
  \includegraphics[height=2.1cm]{img/logo_docker.png}
  \caption{Docker, the containerization technology adopted in Sprint 10}
  \label{fig:docker-logo}
\end{figure}

\runin{A reconsidered architecture decision}
The project had initially recorded a decision to run natively, without containers, justified by
iteration speed on an already-provisioned machine. That decision served development well but left
two gaps: no reproducible deployment, and a production profile that had never actually been
executed.

The decision was therefore superseded rather than silently contradicted: a new record documents the
move to containers, states what it changes, and confirms what it does \emph{not} change. In
particular, three containers are \textbf{not} three microservices: the modular monolith decision
stands. What is containerized is one application, its database and its static server.

\runin{Design decisions}
\textbf{Two build stages, so the toolchain never reaches the runtime image.} The backend image
contains a Java runtime and the application archive, with neither Maven nor sources; the frontend
image contains a web server and the compiled assets, with no Node runtime.

\textbf{Tests are not run during image construction.} Building an image is a packaging step; the
quality gate belongs to the pipeline. Running the suite in both places would double build time
without producing any additional signal.

\textbf{A single origin through the reverse proxy.} The web server serves the application and
forwards \texttt{/api} to the backend container, so the browser contacts one origin. The
cross-origin configuration required by the development setup becomes unnecessary, and the refresh
cookie, restricted to its own path and marked \texttt{SameSite=Strict}, works without any exception.
On this point the containerized deployment is simpler and safer than the development loop.

\textbf{Ordering by health probe, not by declaration order.} A container being \emph{started} is not
the same as a container being \emph{ready}. The database is probed over TCP, because the temporary
server used during initialisation accepts only local socket connections and would otherwise be
reported ready too early. The backend exposes a health endpoint, deliberately unauthenticated but
returning no detail, with a generous startup window because its first run applies the full set of
schema migrations.

\subsection{Implementation}
The exercise is reported in the order it happened: what containerization revealed about the
application, then the pipeline that now runs on every change.


\runin{Defects revealed by the exercise}
Preparing the pipeline exposed three pre-existing defects that native execution had concealed. The
most consequential concerned the frontend build configuration: the production configuration never
substituted the production environment file, so the production bundle embedded the development API
address. On the development machine the application appeared to work, because the bundle was calling
the local backend, while it would have been broken on any other host. The second was a build wrapper
documented in the project files but absent from the repository. The third was an ignore rule that
silently excluded the configuration template from version control, precisely the file the deployment
procedure requires.

That these defects surfaced only when the delivery chain was automated is itself the argument for
automating it.

\runin{Pipeline}
The pipeline separates what must always hold from what is only meaningful on integration branches.
Compilation, the backend test suite, the production frontend build and the construction of both
images run on every proposed change: a component that only breaks after merging is not a gate. The
end-to-end test, which starts the full stack and performs a real authentication through the reverse
proxy, runs on integration branches, where its cost is justified. Image publication is reserved for
the main branch.

The frontend job also carries an explicit guard against the defect described above: it fails if the
development address reappears in the production bundle.

\subsection{Testing}
This sprint has no test class of its own. What it had to verify is that the delivery chain does
what it says, and the chain verifies it by running. The pipeline runs the same 97 tests as
Sprint~9, and adds three checks that only exist once the application is packaged: that the
production frontend builds, that both images build, and that the assembled stack answers.

The production build is the check that caught the worst defect of the sprint.
Figure~\ref{fig:cap-frontend-build} is its output. It reports the size of every bundle and refuses
to hide the one warning it raises: the initial bundle is 694.76~kB, which is 194.76~kB over the
budget set in the Angular configuration. The budget is a warning and not an error, so the build
passes; the overrun is recorded here rather than left out, because it is the next thing the
interface should address.

\begin{figure}[H]
  \centering
  \includegraphics[width=\columnwidth]{img/cap_frontend_build.png}
  \caption{Output of \texttt{npm run build}: the initial bundles, the total, and the budget warning}
  \label{fig:cap-frontend-build}
\end{figure}

Figure~\ref{fig:ci-pipeline} shows where that build sits among the five jobs, and what the
pipeline does once it has passed. The job that matters most is the last verification one: it starts
the whole stack and checks that it answers. That job was run here against the stack itself, and
Figure~\ref{fig:cap-docker-stack} is the result.

\begin{figure}[H]
  \centering
  \includegraphics[width=\columnwidth]{img/cap_docker_stack.png}
  \caption[The stack under Docker]{The stack under Docker: three containers healthy, then the four checks the
           pipeline runs against them}
  \label{fig:cap-docker-stack}
\end{figure}

Three containers, none of them assuming anything of the host: PostgreSQL, the backend, and an nginx
front that serves the built Angular application and forwards the API calls. Each declares a health
probe, and the backend only starts once the database reports healthy, which is what removes the
startup race the native deployment had. The four checks below them are the ones the pipeline runs.
The first is the important one: a real sign-in that travels the whole chain, browser to nginx to the
API to the database, and comes back with a token and the permissions of the account. The other three
confirm that a deep link into the Angular application is served rather than answered with a 404, and
that the translation catalogues are reachable. The token returned by the sign-in is cut short in
the figure: a report should not carry a usable credential, even one belonging to a demonstration
account.

The same checks run on the build server, on a machine that has never seen this project.
Figure~\ref{fig:cap-ci-run} is the run that built the commit this chapter was written on.

\begin{figure}[H]
  \centering
  \includegraphics[width=\columnwidth]{img/cap_ci_run.png}
  \caption{Run~40 of the pipeline on GitHub Actions: four jobs green, the fifth skipped}
  \label{fig:cap-ci-run}
\end{figure}

The run takes five minutes and thirty-nine seconds from the push to the verdict. The two build jobs
go first and in parallel, one minute forty-one for the backend and its 97 tests, thirty-seven
seconds for the production frontend. The images are built next, in forty-seven seconds, and the
end-to-end job then spends two minutes thirty-one starting the stack from those images and running
the four checks of Figure~\ref{fig:cap-docker-stack} against it.

The fifth job carries a grey mark rather than a green one. It is not a failure: publication is
reserved for the main branch, this run is on \texttt{develop}, and the condition on the job
therefore skipped it, exactly as Figure~\ref{fig:ci-pipeline} declares. A skipped job that
should have been skipped is the pipeline behaving as specified.

This figure and Figure~\ref{fig:cap-docker-stack} are the same checks run twice, and the pair
is the point of the sprint. One is the stack on the development machine, where every tool the
project needs happens to be installed. The other is the same stack on a runner that starts empty
and is destroyed afterwards. A deployment that only works on the machine it was built on is the
defect this sprint set out to remove, and the second figure is the evidence that it is removed.

\subsection{Sprint review}
The sprint reviewed itself by failing. Building the pipeline brought out three defects that
running the application by hand had hidden. The worst was a production bundle that still pointed
at the development API address. None of the three appeared until the delivery chain was automated,
which is the best argument for automating it.

\section*{Conclusion}
\addcontentsline{toc}{section}{Conclusion}
Release~4 closed the construction by delivering what functionality alone does not: one coherent
interface, a security model checked by tests, and a deployment anyone can reproduce. The four
releases followed the same order throughout, from foundation to operations, then finance, then
consolidation. Each one could be shown on its own, and together they cover the whole business
logic the Excel workbook used to carry.
