\chapter{Release 1 --- Foundation and Security}

\section*{Introduction}
This chapter presents the first release of the PMS platform. Its purpose is to make the application
usable and secure before any business functionality is built on top of it. It gathers two sprints:
Sprint~1 establishes the technical foundation and authentication, Sprint~2 delivers the dynamic
access control together with the management of users and resources.

At the end of this release, the platform authenticates its users, applies a configurable
authorization policy, and holds the reference data (users, resources, cost rates) that the
operational modules of Release~2 will consume.

% =====================================================================
\section{Sprint 1 --- Technical Foundation and Authentication}

\subsection{Sprint Objective}
Establish the technical skeleton of the backend application and deliver a complete, secure
authentication chain. No business functionality is addressed in this sprint: the goal is to obtain
a running, testable and secured application shell.

\subsection{Functional Scope}
This sprint covers user stories US-01 to US-03 of the backlog
(Table~\ref{tab:backlog}): signing in, the forced password change on first login, and the immediate
revocation of active sessions.

\subsection{Features Implemented}
\begin{itemize}
  \item Modular Spring Boot application skeleton.
  \item Automatic auditing and logical deletion shared by all business entities.
  \item Versioned database schema management through Flyway migrations.
  \item Login by e-mail and password with JWT access token and refresh token.
  \item Immediate session revocation by token version.
  \item Mandatory password change on first login.
\end{itemize}

\subsection{Technical Realisation}

\subsubsection{Modular monolith structure}
The application follows a \textbf{modular monolith} architecture: the code is organised into
independent functional packages, each exposing its own Controller $\rightarrow$ Service
$\rightarrow$ Repository $\rightarrow$ Domain layering. The modules are \texttt{auth},
\texttt{user}, \texttt{project}, \texttt{team}, \texttt{workload}, \texttt{kpi}, \texttt{billing},
\texttt{mission}, \texttt{governance} and \texttt{shared}. This structure allows each subsequent
sprint to add its module without touching the previous ones.

\subsubsection{Base entity and automatic auditing}
All business entities inherit from \texttt{BaseEntity}, which centralises the auto-generated
primary key, the \texttt{createdAt} / \texttt{updatedAt} timestamps managed by \texttt{@PrePersist}
and \texttt{@PreUpdate}, and the \texttt{deleted} marker implementing logical deletion. No data is
ever physically erased, and every repository implicitly filters on \texttt{deleted = false}. This
guarantees the traceability required by the auditability requirement (NFR-008).

\subsubsection{Schema management through Flyway}
The database structure is managed exclusively by Flyway. Hibernate never emits implicit DDL:
the property \texttt{spring.jpa.\allowbreak hibernate.\allowbreak ddl-auto} is set to \texttt{validate}.
The versioned migrations are idempotent and constitute the living documentation of the schema.

\subsubsection{Token issuance}
On \texttt{POST /api/auth/login}, the authentication service verifies the e-mail and compares the
supplied password with the BCrypt hash (strength~12), checks that the account is active, then
issues:

\begin{itemize}
  \item a short-lived \textbf{JWT access token} signed with \texttt{HMAC-SHA512}, carrying the
        e-mail, the token version and the list of permission codes;
  \item an opaque \textbf{refresh token} placed in an \texttt{HttpOnly} / \texttt{Secure} /
        \texttt{SameSite=Strict} cookie.
\end{itemize}

Separating the two tokens, access token in memory and refresh token in a cookie, protects
against XSS attacks: the more powerful refresh token is never reachable from JavaScript.

\subsubsection{Immediate revocation by token version}
Revocation rests on a \texttt{token\_version} field persisted in the \texttt{users} table. The
current version is embedded in every issued token. On each request, the
\texttt{JwtAuthenticationFilter} compares the version carried by the token with the value read from
the Caffeine cache; if they differ, the request is rejected with \texttt{401 Unauthorized}.

Incrementing \texttt{token\_version} therefore invalidates every active session of that identity
instantly: on logout, and on password change, which closes sessions opened on other devices. The
cache avoids a database access on every request while keeping consistency without distributed
state.

\subsubsection{Forced password change on first login}
When an account is created, the administrator sets a temporary password and \texttt{first\_login}
is set to \texttt{true}. The token issued at the first connection carries a restricted right: only
\texttt{POST /api/\allowbreak auth/\allowbreak change-password} is authorised. Once the password is changed,
\texttt{first\_login} becomes \texttt{false} and an unrestricted token is issued.

\subsection{Sprint Outcome}
At the end of Sprint~1 the platform is a running, secured application shell: a user can sign in,
is forced to choose a personal password, and their sessions can be cut off immediately. The
auditing, logical deletion and schema-migration mechanisms are in place and will be inherited by
every module built afterwards.

\subsection{Transition to the Next Sprint}
The application authenticates its users but does not yet distinguish what each of them may do:
the token carries permission codes that nothing populates yet. Sprint~2 therefore builds the
dynamic authorization model that fills this gap, together with the management of the users and
resources it applies to.

\section{Sprint 2 --- Dynamic Access Control, Users and Resources}

\subsection{Sprint Objective}
Deliver the authorization model that structures the whole platform, the
``Role $\rightarrow$ Permission $\rightarrow$ Module'' chain introduced in
Section~\ref{sec:rbac}, and the administration screens that feed it with reference data.

\subsection{Functional Scope}
This sprint covers user stories US-04 to US-07: assigning permissions to roles, adapting the
interface to the rights held, managing user accounts, and recording resources with their yearly
cost rate.

\subsection{Features Implemented}
\begin{itemize}
  \item Permission--Role--User model persisted in the database.
  \item Propagation of permissions to Spring Security and protection of every endpoint.
  \item Navigation menu built dynamically from the rights held.
  \item User account management: creation, modification, activation and deactivation.
  \item Resource management and entry of the yearly loaded cost rate (TCC).
\end{itemize}

\subsection{Technical Realisation}

\subsubsection{Permission--Role--User model}
Access control is \textbf{entirely dynamic}: permissions are not hard-coded in the application. The
\texttt{role\_permissions} table associates a set of permissions with a role. A user holds a single
active role, but that role can be reconfigured at any time by the administrator without
redeployment.

A dedicated migration initialises the four default roles (Administrator, Director, Project Manager,
Developer) with eighteen permission codes spread over seven modules (\texttt{ADMIN},
\texttt{PROJET}, \texttt{EQUIPE}, \texttt{CHARGE}, \texttt{FACTURATION}, \texttt{KPI},
\texttt{GOV}).

\subsubsection{Propagation to Spring Security}
The \texttt{JwtAuthenticationFilter} reads the permission codes from the token and converts them
into \texttt{SimpleGrantedAuthority} objects. Every REST entry point is then protected by an
annotation of the form:

\begin{verbatim}
@PreAuthorize("hasAuthority('CREATE_PROJECT')")
\end{verbatim}

The absolute rule is that \textbf{no role name is ever tested in application code}: only permission
codes are used. This is what makes the authorization policy a matter of data rather than of source
code.

\subsubsection{Dynamic menu}
The \texttt{GET /api/me/context} endpoint returns, for the authenticated user, the list of their
permissions together with their profile information. The Angular frontend uses this response to
build the navigation menu: an item is displayed only if the user holds the required permission
code. The interface therefore reflects the authorization policy automatically, with no duplicated
rule on the client side.

\subsubsection{Users and resources}
The \texttt{user} module manages accounts (creation by the administrator with a temporary password,
modification, activation and deactivation, role assignment) and the human resources with their
daily rate and loaded cost rate. The distinction between the two notions is deliberate: a resource
represents a cost-bearing capacity, which may or may not be linked to a platform account. Object
conversions between entities and DTOs are handled by MapStruct mappers.

The loaded cost rate is recorded \textbf{per resource and per year}, so that the cost of a man-day
uses the rate of the year in which the effort was booked, a requirement drawn directly from the
Excel workbook.

\subsection{Sprint Outcome}
The platform now knows not only \emph{who} the user is but \emph{what they may do}, and the
authorization policy can be modified by an administrator without touching the code. The reference
data required by the business modules (users, resources, yearly cost rates) is in place.

\subsection{Transition to the Next Sprint}
Release~1 delivers a secured and administrable platform, but it manages no project yet. Release~2
opens operational steering, starting in Sprint~3 with the central entity of the whole domain: the
project.

\section*{Conclusion}
Release~1 established the foundations on which the entire platform rests: a modular application
skeleton with auditing and controlled migrations, a robust authentication chain, and above all a
dynamic authorization model that makes the security policy configurable data rather than compiled
code. The next release exploits this foundation to deliver the operational management of projects
and workload.
